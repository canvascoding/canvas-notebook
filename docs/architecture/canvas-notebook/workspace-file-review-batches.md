# File review batches

File action reviews display source/destination paths and Markdown changes first. Folder descendants and technical diagnostics are expandable. An individual Move, Rename, or Delete opens source/destination paths immediately and queues a current one-action background check; multiple reviews use the same planning and execution path. Copy keeps its existing fenced executor.

## Approval and execution

1. The UI submits up to 50 distinct review IDs to `POST /api/files/operation-reviews/checks` and receives a durable check ID with HTTP 202. Submission validates database references and permissions without traversing workspace files. `GET /api/files/operation-reviews/checks/{checkId}` returns queued/checking/ready/blocked/failed and the completed immutable batch preview. A read-only worker takes the workspace lock, resolves current reviewer permissions, and builds one virtual final workspace state. Active identical selections deduplicate per user/workspace; 90-second renewable SQL leases allow a fresh server to resume a check after interruption. Closing the dialog keeps polling; reopening/reloading restores only the authenticated session's scoped check ID and validates it with the server. “Check again” starts a fresh check. The legacy batch preview endpoint remains compatible. Conflicting or overlapping roots are blocked. Link writes affecting the same document are combined against its original bytes.
2. `action: accept`, the batch ID, and the exact plan ID reserve all reviews and persist a queued job in one database transaction. Approval performs a targeted identity/content/Yjs fence on the known plan inputs. The execution worker independently rebuilds and validates the full graph before its first file write. Changed effects become `needs_review`; approval never silently accepts a replacement plan. Unrelated pre-existing diagnostics do not alter the mutation fingerprint; current resolution safety is still checked.
3. The long-lived custom Node server initializes the batch worker after its collaboration bridge. SQL leases order jobs per workspace; the executor also takes the kernel workspace lock. The worker resolves the reviewer's current permissions before execution and before further writes.
4. Every path mutation and document write has a private fsynced intent/receipt manifest under `DATA/workspace-operation-batches`. Backups exist before the first mutation. Restart resumes only steps with proven before/after state. An uncertain mutation remains recoverable without replaying it blindly.
5. Completion requires the final file state and Markdown file projections to match the approved result. Running jobs remain accessible from the Notification Center after closing the review.

The database stores the approved plan, job status, progress, and lease. The private manifest stores the exact plan, source trees, backup references, collaboration preflight fences, step receipts, and Undo state. Keep both with workspace backups.

## Link behavior

Moves preserve links between the final locations of source and target. Deletes remove link wrappers in surviving Markdown documents while preserving visible text and surrounding prose. Parser node spans handle inline links/images, reference usages/definitions, and Wiki links/embeds. External links and code examples are preserved. Unsupported or uninspected affected sources block the preview.

The shared link rules apply to single actions, batches, background checks, execution and Undo:

- Markdown paths resolve relative to the source document; a leading `/` means the workspace root. Wiki paths with a slash (including `./` or `../`) identify a concrete intended path. Bare Wiki names/titles/aliases, including `[[name.md]]`, use the existing name resolver. A newly functioning binding must resolve uniquely to the recorded file identity; existing unresolved lookups follow the warning rules below. Adding an extension alone does not prove a workspace-root intention. External URLs, anchors and code examples retain their existing parser behavior.
- A functioning link must continue to reach the same file identity after the source or target moves. Only parser target spans change; relative paths are rebased against the final document location.
- A previously missing exact path remains a warning when its intended logical target stays unchanged. Moving its source or selected parent directory rebases that path even when the target file is absent. A bare missing Wiki name stays a warning if the lookup remains missing.
- A previously missing explicit path may become uniquely resolved to the exact approved destination. This is reported separately as a restored link, even when its literal needs no rewrite. A new binding inferred only from a Wiki name/title/alias remains blocked.
- Existing ambiguity is a warning only when the same candidate file identities remain. A newly resolved ambiguity, new candidate, wrong target, or previously functioning link becoming missing blocks approval. Unsupported or unevaluated affected sources also block.
- Deletion removes links to deleted files and exact missing descendants of a deleted directory. Labels and prose remain. Bare Wiki names are never guessed as descendants.

The review shows selected root paths while the check runs, changed/restored links when it completes, and collapsed existing warnings. The completed preview appears before collapsed selection and backup sections; its root paths are displayed once. A matching ready selection exposes one primary approval button. A true blocker offers “Open document” through the normal guarded workspace/editor navigation and “Check again” after correction. Selection changes disable approval of an older selection.

Manual deletion in the file browser uses this same planner. When cleanup changes or blockers exist, it creates a persistent user review and keeps the files and selection until approval. A linked deletion then runs through the batch worker. Link-free deletion keeps the existing trash response. Confirmed deletion receipts publish file-tree events; completed Undo publishes restoration events.

Active Yjs link writes use the document's persisted representation. Plain text uses exact target-span edits; rich Markdown uses the existing adapter after a clone proves the approved bytes round-trip exactly, preserving its representation and stable node identities. Both paths validate the current content hash and spans again under the room mutation lock. Active documents with CRLF or a BOM remain unsupported by this exact-edit service and fail before path writes. The worker materializes acknowledged Yjs changes through the existing transactional checkpoint API within its reentrant workspace lock. A separate queued projector would otherwise wait for that same lock. Completion verifies both the authoritative collaboration state and the serialized file bytes. The background projector reloads the active document, generation, and pending receipts after obtaining the workspace lock, so a waiting projection cannot replace a completed checkpoint again.

Changing a referenced document marks dependent open reviews as outdated. Refresh creates an immutable successor and retains the original preview. Rebinding a moved source follows chronological receipts from completed operations, including A → B → C. Final destination inode/hash and collaboration document ID/generation are recorded after all checkpoints. This supports atomic Markdown replacements while refusing substituted files or documents. Later changes without acknowledged operation receipts remain blocked; a path coincidence is insufficient. An unrelated file reusing the original source slot never wins over a verified moved endpoint. If the original lineage cannot be proved and that slot is occupied, Refresh and combined preview return an explicit conflict. Combined previews share one snapshot and transition history, preserve the original review references, and store normalized current paths for worker revalidation. The refreshed UI explains changed paths, link counts, and readiness. Changed effects require a fresh explicit approval.

## Recovery and Undo

Resume uses the existing batch ID and exact plan. It never silently approves a rebuilt plan. A failed approved job exposes an explicit retry action. Only the recorded reviewer can resume their approved job, and their current permissions are checked again. An authorized current reviewer may request Undo; any interrupted Undo remains bound to that reviewer. Undo first checks current paths, source-slot collisions, original link-document contents, and the virtual inverse link graph. New incoming links or user edits that the approved inverse would damage cause a conflict before any reverse write. Restored links retain private original document bytes and identity/hash fences; Undo may return exactly those recorded links to their original missing state, without allowing newer backlinks to break. Restore includes trashed files and the original Markdown contents; private deleted-document snapshots are excluded from public preview responses.

## Verification

`npm run test:files:operation-batches` runs planner, filesystem executor, PostgreSQL-compatible queue/lease, immutable refresh, UI/client, notifications, empty-document restoration, and the complete collaboration projection regression suite.

`npm run test:files:operation-batches:e2e` uses the managed local PostgreSQL server and bootstrap credentials from `CANVAS_ENV_FILE` (defaults to the skill's private host-development environment). Each run creates a uniquely named disposable database and private data directory, then uses the real migrations and bootstrap command. This prevents other checkouts' durable workers from claiming the test jobs against their different filesystems. The runner owns one Notebook process on port 3001, refuses an occupied port, accepts `CANVAS_BATCH_E2E_PORT` to use another free port, starts no containers, and stops only its own process. Browser cases cover shared backlinks, mutually dependent moves, mixed deletion, twenty reviews, stale refresh, consecutive moves with atomic Markdown checkpoints, reused original paths in both Refresh and combined approval, actual file-browser deletion, the reported atelier folder move, repaired future-path links, preserved old missing targets, exact missing descendant cleanup, background check close/reload, actionable ambiguity repair, late new backlinks, collisions, duplicate approval, Undo, and authorization. Additional scenarios queue an approval while the server is stopped and kill a disposable executor process after one receipted physical mutation, then verify a fresh server completes the remaining steps. A third scenario queues a read-only check with the server stopped, verifies the restarted worker produces a ready preview without changing any file, and only then explicitly approves it.

The private instance uses supported Community deployment settings and disables onboarding because these tests exercise personal-workspace file reviews rather than Team activation or AI-provider setup. Existing licensed instances and their certificates are untouched. The runner retains its private server log and restart evidence under the ignored `.playwright-mcp/file-review-batches` directory. Playwright screenshots and failure diagnostics use `test-results`.

Each browser run owns disposable personal workspaces identified by a unique run ID and cleans them up even after a browser failure. The private database and data directory are removed after the owned server stops. The suite defines 19 browser scenarios and three real process restart scenarios.
