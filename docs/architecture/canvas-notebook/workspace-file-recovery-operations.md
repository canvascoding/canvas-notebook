# Datei-Wiederherstellung und Backup-Betrieb

Stand: 2026-09-28. Diese Bestandsaufnahme beschreibt implementierten Code und die lokale Team-Seat-Prüfung; sie ist kein Nachweis eines vollständigen Disaster-Restore.

## Schutzbereiche und Aufbewahrung

| Mechanismus | Inhalt und Zugriff | Aufbewahrung und Grenze |
| --- | --- | --- |
| File Version Center | Historische Markdown-/Textversionen mit Compare/Restore im bestehenden Review Center. | Rohe Version höchstens 1 MiB; automatische Checkpoints: 90 Tage, weitere Mengen- und Speichergrenzen in `app/lib/file-version-center/policy-v1.ts`. Für größere Dateien ist dies keine Sicherung. |
| Workspace-Papierkorb | Browser- und Agent-Delete legen Pfade unter `/data/.trash/workspaces/` ab. Browser-Delete bietet acht Sekunden lang einen Undo-Toast; ein einzelner Eintrag kann per `POST /api/files/trash/{entryId}/restore` wiederhergestellt werden, solange sein ursprünglicher Pfad frei ist. | `expiresAt` ist standardmäßig 30 Tage; `WORKSPACE_TRASH_RETENTION_DAYS` erlaubt 1–3650 Tage. `purgeExpiredWorkspaceTrash()` existiert, aber im Repository ruft kein Scheduler/Produktpfad diese Funktion auf. Ablauf bedeutet derzeit daher **nicht** nachgewiesene automatische Löschung. Eine dauerhaft auffindbare Desktop-Papierkorbliste fehlt. |
| Operations-Snapshot | Vor destruktivem Overwrite/Move gesicherte Datei oder Verzeichnisstruktur in `/data/.workspace-operation-backups/`, mit SHA-256 pro Datei. Workspacegebundenes `GET /api/files/operation-backups?limit=50&cursor=…` listet Metadaten; `GET /api/files/operation-backups/{backupId}` liest einen Eintrag; `POST` auf dieselbe ID stellt ihn am ursprünglichen oder einem freien `targetPath` wieder her. | `retention: until_manual_cleanup`; kein automatischer Prune und keine Speicherquote. Restore prüft alle Payload-Hashes und überschreibt keinen bestehenden Pfad. `.docx` wird vom API-Restore ausgeschlossen und braucht den Office-Workflow. Die Snapshot-Manifestgröße ist auf 8 MiB begrenzt, die Nutzdaten selbst werden gestreamt. |
| Full Backup | Manuell per `canvas-notebook backup create [--output <pfad>]` oder Admin-API: ZIP mit PostgreSQL-Custom-Dump und den nicht ausgeschlossenen `/data`-Dateien. Enthält auch Secrets, Public-Link-Tokens, Papierkorb und Operations-Snapshots; das Archiv ist unverschlüsselt. | Der wartende CLI-Pfad prüft und ersetzt ein stabiles `latest` und entfernt anschließend Job-Artefakte, sofern `--keep-job-artifacts` nicht gewählt wurde. Admin-API-Jobs haben eigene Archive und keinen automatischen Prune. `CANVAS_BACKUP_TARGET_DIR` kann das Latest-Ziel ändern. Es gibt keinen konfigurierten Zeitplan. |

Ein Full Backup umfasst weder VM/OS noch Docker-Images, App-Binaries, Host-Konfiguration oder CLI-Installation. Der Datenbank-Dump ist konsistent, die gleichzeitig gelesenen Dateien sind ein `online_best_effort`-Stand. Eine atomare, gemeinsame Momentaufnahme von Datenbank, Yjs-State und Dateisystem ist damit nicht belegt (`app/lib/backups/types.ts`, `app/lib/backups/full-backup-service.ts`).
Der Scanner spart nur bekannte technische Verzeichnisse am Datenroot bzw. unter `system/` aus. Gleichnamige Ordner innerhalb eines Nutzer-Workspace (auch `.git`, `node_modules`, `.next`, `cache`, `temp` und `logs`) werden gesichert. Das verhindert stillen Verlust von Nutzerdateien und Versionshistorie, kann Full Backups bei großen Workspace-Repositories aber deutlich vergrößern.

## Praktischer Restore-Status

Für einen einzelnen Overwrite ist der Operations-Snapshot der schnellste belastbare Pfad: im aktiven Workspace die Backup-ID suchen, Metadaten prüfen, an einen **freien** Pfad wiederherstellen und die Datei mit dem aktuellen Stand vergleichen. Der API-Restore ist auditierbar und meldet `RESTORE_COLLISION`, wenn der Zielpfad bereits existiert. Für Delete lässt sich der Papierkorbeintrag mit seiner Trash-ID zurückholen; der Browser bietet den Undo-Toast direkt nach dem Löschen. Das File Version Center deckt die kleinere, versionierte Datei ab.

Für eine **abgeschlossene, workspace-interne Rename-/Move-Operation** kann das Review Center zusätzlich ein zusammenhängendes Undo ausführen: Es prüft den gesicherten Quellinhalt, den heutigen Zielbaum und die exakten Link-Hashes, erstellt einen vollständigen inversen Plan und führt diesen als neue, auditierte Dateioperation aus. Sobald eine Datei oder ein Link zwischenzeitlich geändert wurde, gibt es `UNDO_CONFLICT` statt eines stillen Überschreibens. Direkt nach einer Freigabe kann die kollaborative Markdown-Projektion noch ausstehen; die Oberfläche prüft die Undo-Verfügbarkeit deshalb erneut. Copy, ältere Operationen ohne Undo-Snapshot, Cross-Workspace-Vorgänge und `needs_recovery` haben derzeit kein automatisches operationsweites Undo. Für letztere bleibt eine gezielte Prüfung von Journal, Staging und aktuellen Dateien nötig.

Die Listen-API prüft Manifest/Workspace-Zuordnung; `status: manifest_valid` ist ausdrücklich noch kein Payload-Integritätsnachweis. Ein beschädigtes Manifest bleibt als `status: unavailable` mit ID sichtbar. Erst der Restore prüft die Nutzdaten vollständig. Ein einzelner Snapshot-Restore setzt keine zugehörigen Markdown-Link-Edits zurück.

Für Full Backup gibt es Erstellung, Download und `inspectFullBackupArchive()`, jedoch **keinen** Full-Instance-Restore-Executor oder `backup restore`-CLI-Befehl im Repository. Das Feld `canRestore` der Inspection bedeutet lediglich, dass die geprüften Voraussetzungen erfüllt erscheinen; es beweist keine durchgeführte Wiederherstellung. Die Inspection prüft den SHA-256 des Datenbank-Dumps, nicht jeden im Manifest genannten `/data`-ZIP-Eintrag. Ein vollständiger Restore lässt sich ohne separat implementierten und geprobten Ablauf nicht zusichern.

## Speicher- und Fehlerverhalten

- Operations-Snapshots schreiben zunächst in ein privates temporäres Verzeichnis, prüfen Bytes/Hashes, synchronisieren und veröffentlichen es erst danach. Schlägt eine Sicherung wegen `ENOSPC`, Quellenänderung oder unsicherem Pfad fehl, muss der aufrufende destruktive Pfad vor seiner Mutation abbrechen; die temporäre Ablage wird entfernt. Der vorhandene Test belegt große Markdown-, Binär- und Verzeichnis-Restores samt Korruptions- und Kollisionssperre. Er simuliert keinen echten vollen Datenträger.
- Der Linkindex lässt Markdown-Quellen über 4 MiB aus. Die Recovery-Staging-Ablage begrenzt ein Markdown-Dokument auf 4 MiB, alle Dokumente zusammen auf 64 MiB, die Anzahl auf 256 und ihr Manifest auf 8 MiB (`workspace-link-limits.ts`, `workspace-operation-staging.ts`). Eine unvollständige Vorschau bleibt blockiert; große Binärdateien können trotzdem als Ziele vorkommen und im Snapshot gestreamt werden.
- Full-Backup-Jobs serialisieren über Lockfile. Ein Fehler beim ZIP-Schreiben markiert den Job als fehlgeschlagen und entfernt das teilweise Archiv; ein Fehler beim Kopieren/Prüfen der Latest-Staging-Datei lässt das bisherige Latest bestehen. Archiv und Latest-Metadaten werden aber in **zwei** Rename-Schritten ersetzt; ein Crash zwischen ihnen kann eine inkonsistente Paarung hinterlassen. Außerdem können API-Jobs ohne Prune Speicher ansammeln. Ausreichender freier Speicher für Dump, Job-ZIP und Latest-Staging muss betrieblich überwacht werden.
- Der Papierkorb nutzt auf demselben Dateisystem `rename`. Beim `EXDEV`-Fallback wird kopiert und danach gelöscht; ein Fehler während dieser Kopie kann eine teilweise Kopie im Trash hinterlassen, während die Quelle noch existiert. Es gibt keinen im Code nachgewiesenen automatischen Cleanup für diesen Fall.

## Bekannte Link-Grenzen

Inline-Markdown-Links/-Bilder, Referenzdefinitionen und Wiki-Links/-Embeds werden durch den gemeinsamen Parser verarbeitet. Externe Web-/Mail-/Data-Ziele, reine Anker und Code werden absichtlich nicht umgeschrieben. HTML-`href`/`src`, nicht unterstützte Schemes, Query-Parameter und nicht parsebare Zielsyntax erscheinen als `not-evaluated`; fehlende, mehrdeutige oder den Workspace verlassende Ziele blockieren eine vollständige Ausführung. Frontmatter wird nicht als Markdown-Quellinhalt ausgewertet. Ein Cross-Workspace-Move und Cross-Workspace-Copy mit Verweisen auf nicht kopierte Ziele sind nicht automatisch reparierbar. Manche Wiki-Zielnamen und Legacy-Notebook-Zielformate lassen sich nicht formatgetreu umschreiben; sie bleiben als `unsupported-target-format` blockiert (`workspace-local-link-parser.ts`, `workspace-file-operation-planner.ts`).

Die Agenten-Review-Pflicht gilt für die workspace-lokalen Dateioperationen im integrierten Agent-Executor. PDF-Overwrite über Spezialtools und Dateiaktionen eines Agenten über einen angemeldeten Browser haben derzeit keine verlässliche Agent-Provenienz und werden deshalb nicht als durch dieses Review-Gate geschützt ausgewiesen. Die Ereignismetrik `workspace_file_operation_events_total` zählt unvollständige Linkpläne, Konflikte, fehlgeschlagene Ausführungen und Recovery-Fälle mit festen Labels für Scope, Operation, Phase und Ergebnis; Pfade und Inhalte werden nicht als Labels protokolliert.

## Verifikation am 2026-09-28

- `docker ps --filter label=io.canvas.local-prod=true`: genau ein lokaler Team-Seat-Stack mit Notebook, Control-Plane-Web/API und PostgreSQL; alle vier Container meldeten `healthy`. Im Notebook-Container ist `pg_dump 18.4` vorhanden. Es wurde kein Container gebaut oder neu gestartet.
- `npx tsx --conditions react-server scripts/workspace-operation-backup-list-test.ts`: Pagination, Workspace-Isolation, beschädigtes Manifest und Eingabevalidierung erfolgreich.
- `npm run test:cli:backup`: erfolgreich, benutzt ausdrücklich Docker-Mocks; belegt keinen realen Dump oder Restore.
- `npm run test:backup:full`: erfolgreich mit einem isolierten Fake-`pg_dump`; prüft parallele Job-Sperre, Archivinhalt einschließlich technisch benannter Ordner in neuen und Legacy-Workspaces, Dump-Inspection, Latest-Promotion, Beibehaltung des alten Latest bei Prüffehler und Prune. Der zuvor fehlende Test wurde ergänzt. Es wurde weder ein echter PostgreSQL-Dump noch ein Full Restore ausgeführt.
- `npm run test:files:operation-undo`, Review-Backend/UI-, Executor-, Backup- und Preview-Tests sowie `npm run lint` und `npm run build`: erfolgreich. Lint meldet sieben bestehende Warnungen außerhalb dieser Änderung, keine Fehler.
- Host-Dev/Playwright: Ein freigegebener Agent-Move wurde mit repariertem eingehendem Markdown-Link ausgeführt und anschließend per Undo samt Link zurückgesetzt. Ein zwischenzeitlich verändertes Ziel führte zu `UNDO_CONFLICT`/HTTP 409 ohne Mutation; direkter Rename und Undo liefen ebenfalls durch. Ein Snapshot wurde aus dem Recovery-Panel an einen freien Pfad restauriert. Bei 390 px blieb der mobile Dialog ohne horizontales Überlaufen. Die angelegten Testdateien, Review-Zeilen und Test-Snapshots wurden anschließend gezielt entfernt. Für diese Prüfung wurde kein Container gebaut oder neu gestartet.

Vor einer Aussage „Full Restore verfügbar“ sind mindestens ein Restore-Executor mit Offline-/Maintenance-Gate, ein Probelauf in einer isolierten Zielinstanz und per-Datei-Integritätsprüfung nötig.
